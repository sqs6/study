## 0. 一句话结论

> **IoT = 让"东西"接入互联网（感知 → 网络 → 平台 → 应用）**。
> 对网安来说，它同时是**最容易被攻破的一类资产**（出厂不管、长期不更新、物理口没关）和**最能训练系统性安全思维的载体**（软硬件协议云的完整链路都能摸到）。

## 1. IoT 是什么

### 1.1 定义与边界

**IoT（Internet of Things）**：把传感器、执行器、机器、车辆等**实体对象**接入互联网，使其具备 **感知、传输、处理、远程控制** 四种能力。

**和"传统 IT"的区别**：

|      | 传统 IT               | IoT                        |
| ---- | ------------------- | -------------------------- |
| 终端   | PC/服务器/手机（数量少、有专人管） | 海量小设备（**数量 ≫ 传统设备**）       |
| 管理   | 有 IT 部门、有补丁流程       | **几乎没人管**，出厂即"半成品"         |
| 网络   | 有线为主、可控             | 大量无线、弱隔离                   |
| 安全基线 | 相对高                 | **极低**（默认口令、久不更新）          |
| 生命周期 | 3–5 年               | **5–10 年+**，很多设备到死都不更新     |
| 攻击后果 | 丢数据                 | 丢数据 + **物理世界后果**（门锁、车辆、工厂） |

**边界模糊处**：

- **云计算** = 计算资源的交付方式；**IoT** = 对象接入网络的方式。两者**正交**（IoT 常用云做平台）
- **边缘计算** = 计算位置的下沉，是 IoT 的架构选择之一
- **IIoT（工业 IoT）** = IoT 在工业场景（可靠性、实时性、安全要求更高）
- **IoMT（医疗 IoT）**、**V2X（车联网）** = 垂直行业变体

### 1.2 一次数据的完整旅程

用"宿舍温湿度监测"举例，走一遍全链路：

```
[传感器 DHT22] 采样 → [MCU ESP32] 转换/滤波
        ↓ Wi-Fi (802.11)
[家庭网关/路由器] 转发 → [公网]
        ↓ MQTT over TLS (8883)
[云 IoT 平台] 鉴权 → 设备影子更新 → 时序库入库 → 规则引擎判断
        ↓
[手机 App / Web 看板] 展示 → [你] 看到温度 26℃

反向（下行）：你的手机 → 云 → 策略下发 → MQTT publish → ESP32 收到 → 继电器动作
```

**这条链路上每一个环节都是攻击面**，这正是 IoT 安全的"系统性"所在。

### 1.3 规模与现实

- 全球 IoT 设备已达**百亿量级**，**数量早已超过非 IoT 设备**（"物"比"人"多）
- 家庭与办公场景里，**路由器、摄像头、智能插座、打印机**是保有量最大的一批
- 工业/车载场景虽然数量少，但**单点影响更大**
- 现实结论：**绝大多数 IoT 设备是"一次性"安全**——出厂时能用，之后没人管

## 2. IoT 的四层架构

### 2.1 感知层

- **传感器**：温湿度、光照、人体红外、门磁、水浸、振动、气体、GPS、加速度计
- **执行器**：舵机、继电器、电机、电磁锁、LED、蜂鸣器
- **载体**：MCU（ESP32/STM32）→ **"端"**
- 安全关注：**物理拆解即可读取传感器与 Flash**、调试口未关、固件明文

### 2.2 网络层

- **传输**：Wi-Fi、BLE、Zigbee/Thread、LoRa、NB-IoT(4G)、以太网、蜂窝、以 RS-485/CAN 为代表的现场总线
- **协议**：MQTT、CoAP、HTTP、Modbus、OPC UA、CAN、MQTT-SN
- **寻址与标识**：IP、MAC、MQTT clientId、证书 CN
- 安全关注：**明文传输**、弱认证、**topic 越权**、网关被攻破后横向移动

### 2.3 平台层（云）

- **设备注册与鉴权**（一机一密 / 一机一证）、**设备影子（Device Twin）**
- **消息总线 / Broker**（EMQX、Mosquitto、云厂商托管服务）
- **时序数据库**（InfluxDB、TDengine、TimescaleDB；**OceanBase 的时序方向可关注**）
- **规则引擎 / 告警 / 数字孪生 / 报表**
- **OTA 升级服务**（最关键的安全组件）
- 安全关注：**多租户隔离、API 鉴权、密钥托管、后台权限边界**

### 2.4 应用层

智能家居、智慧城市/园区、工业监测与预测性维护、车联网、智慧农业、远程医疗、可穿戴、共享充电桩、智慧水利……

安全关注：**越权访问他人设备**（最常见的"小漏洞"）、**API 不鉴权**、数据泄露（摄像头、位置、健康数据）

### 2.5 端-边-云-网：一张全景图

```
                    ┌──────────────────────────┐
                    │        应用层 App/Web      │
                    └────────────┬─────────────┘
                                 │
              ┌──────────────────┴──────────────────┐
              │           平台层（云）               │
              │  设备影子 · Broker · TSDB · 规则引擎   │
              │  身份鉴权 · OTA 签名校验 · 审计日志    │
              └──────────────────┬──────────────────┘
                                 │  MQTT/HTTPS
        ┌────────────────────────┴────────────────────────┐
        │                 网关 / 边缘节点                  │  ← 这里能做协议转换、
        │        （家庭路由、运营商网关、工业边缘盒子）      │     流量过滤、局部推理
        └────────────────────────┬────────────────────────┘
                                 │  Wi-Fi / BLE / LoRa / 4G
        ┌────────────────────────┴────────────────────────┐
        │            端（MCU / SoC + 传感器）              │  ← 攻击面从这里开始
        │   ESP32 / STM32 / 模组 · 固件 · 安全启动 · 密钥    │
        └─────────────────────────────────────────────────┘
```

## 3. 硬件与无线选型

### 3.1 设备形态

| 形态               | 算力                       | 例子          |
| ---------------- | ------------------------ | ----------- |
| **MCU 节点**       | 几十~几百 MHz，数百 KB RAM      | 传感器、开关、灯、门锁 |
| **模组**           | MCU + 射频 + 认证（CE/SRRC）   | 厂商买模组省射频设计  |
| **边缘网关**         | ARM SoC / x86 / Linux    | 协议转换、多路汇聚   |
| **嵌入式 Linux 设备** | Cortex-A + Linux + 完整网络栈 | 路由器、摄像头、NVR |
| **工业 PLC/控制器**   | 专用实时 OS                  | PLC、RTU、DCS |

> 🔗 层次越往上，**操作系统越完整、攻击面越大但也越好研究**（能用 IDA/GDB/Firmadyne）；越往下，**更贴近硬件、更难但更"纯"**。

### 3.2 无线技术对比表

| 技术                    | 频段              | 距离                | 速率          | 功耗  | 典型场景                 |
| --------------------- | --------------- | ----------------- | ----------- | --- | -------------------- |
| **BLE**               | 2.4G            | 10–100 m          | 1–2 Mbps    | 很低  | 手环、标签、耳机、蓝牙注入研究      |
| **Wi-Fi**             | 2.4/5G          | 30–100 m          | 高           | 中   | 家庭/办公主场景、ESP32 默认    |
| **Zigbee**            | 2.4G            | 10–100 m（Mesh 扩展） | 250 kbps    | 低   | 全屋智能（米家等）            |
| **Thread**            | 2.4G (802.15.4) | Mesh              | 250 kbps    | 低   | 新一代 Matter 生态        |
| **LoRa**              | 433/868/915M    | **数公里**           | 0.3–50 kbps | 极低  | 农业、园区、抄表             |
| **NB-IoT / LTE-M**    | 蜂窝              | 运营商覆盖             | 低速          | 低   | 无 Wi-Fi 环境的抄表/追踪     |
| **Sub-GHz (315/433)** | <1G             | 百米级               | 低           | 极低  | 遥控器、车库门、门磁           |
| **RFID**              | LF/HF/UHF       | 近场~10m            | —           | 极低  | 门禁卡、标签（**安全研究高发区**）  |
| **CAN**               | 有线总线            | 车/机床内             | 1–8 Mbps    | 低   | 汽车、**工控**（**无原生安全**） |

> 💡 **选型通则**：距离↑ → 速率↓、功耗↑；**凡是用电池的，优先考虑 BLE/LoRa/NB-IoT**。

### 3.3 低功耗与电池预算

- **休眠档位**：Active → Modem-sleep → Light-sleep → Deep-sleep → Shutdown
- **设计范式**：**"睡得多、醒得少、醒得短"** —— 深睡 µA 级，唤醒后采样 + 上传 + 立刻睡
- **能量采集**：光伏、振动、射频能量（无电池设备）
- **安全含义**：**低功耗 = 更长的暴露周期**（同一颗电池撑一年 = 被扫描到的机会多十倍）；且**深度睡眠中的设备内存仍可能被物理读取**

## 4. 协议层：IoT 的"通用语"

### 4.1 MQTT 详解

**MQTT**（OASIS 标准）= 事实上的 IoT 消息标准。**发布-订阅**模型：

```
[设备 A] --publish--> [Broker] --subscribe--> [手机 App]
  topic: home/room1/temp     topic: home/room1/#
```

| 概念               | 说明                                            |
| ---------------- | --------------------------------------------- |
| **Broker**       | 中枢（Mosquitto、EMQX、云托管）。**它是单点信任核心**           |
| **Topic**        | 层级主题名，如 `home/room1/temp`；通配符 `+`（一层）、`#`（多层） |
| **QoS 0/1/2**    | 0=最多一次；1=至少一次（可能重复）；2=恰好一次（最慢）                |
| **Retained**     | Broker 保留最后一条消息，新订阅者立刻收到（状态同步常用）              |
| **Keepalive**    | 心跳间隔，断开判定                                     |
| **Will Message** | **遗嘱消息**：设备异常掉线时由 Broker 代发（常用于"设备离线"告警）      |
| **端口**           | 1883 明文 / **8883 TLS** / 9001 WebSocket       |

**MQTT 的安全要害**：

1. **认证**：clientId + username/password（**很多设备共用一组全局账号** → 一泄露全网沦陷）
2. **授权**：**ACL 按 topic 限制** —— 没配 ACL 的话，一台设备能读写**所有设备的数据**
3. **加密**：MQTT over **TLS**；老设备常直接明文 1883 → 抓包即得明文
4. **Broker 是高价值目标**：拿下 Broker = 拿到全部设备流量的控制权

### 4.2 其他协议

| 协议               | 传输      | 特点                                    | 典型场景          |
| ---------------- | ------- | ------------------------------------- | ------------- |
| **CoAP**         | **UDP** | 极简 REST 风格，配 **DTLS**；`Observe` 机制省流量 | 受限网络（NB-IoT）  |
| **LwM2M**        | CoAP    | OMA 标准，设备管理模型（Bootstrap/Registration） | 运营商 IoT       |
| **HTTP / HTTPS** | TCP     | 通用、调试方便，但**头重**、长连接弱                  | 低频上报、OTA 升级   |
| **MQTT-SN**      | UDP     | 简化版 MQTT，给无 IP 的传感器网                  | 低功耗 SensorNet |
| **Modbus**       | TCP/串口  | 工业事实标准，**完全无认证无加密**                   | 工控 PLC        |
| **OPC UA**       | TCP     | 工业现代标准，支持证书与订阅                        | 工业互联          |
| **CAN / UDS**    | 总线      | 汽车诊断与控制，**无内置安全**                     | 车联网           |

### 4.3 传输安全：TLS / DTLS

- **MQTT over TLS（8883）/ CoAP over DTLS** 是底线要求
- 证书体系：**一机一证**（设备级证书）优于共享账号
- **常见错误**：自签证书不校验、只做单向 TLS、证书过期无人管、TLS 版本过旧
- **自签 CA 的现实困境**：设备量大了以后，证书签发/轮转/吊销（CRL/OCSP）本身就是难题——这正是**"证书工厂"成为专门岗位**的原因

### 4.4 协议层的典型攻击

| 攻击             | 手法                 | 后果          |
| -------------- | ------------------ | ----------- |
| **明文嗅探**       | 抓 1883 端口流量        | 拿到设备数据与账号口令 |
| **topic 越权**   | 订阅 `#` 或他人 topic   | 读到/伪造所有设备数据 |
| **伪造发布**       | 用偷来的凭据 publish 假数据 | 触发错误控制、告警风暴 |
| **Broker 弱配置** | 匿名可连、无 ACL         | 全网设备沦陷      |
| **重放**         | 抓包后重发控制指令          | 重复开门/启动     |
| **拒绝服务**       | 连接洪泛、遗嘱消息风暴        | 设备批量离线      |
| **协议解析漏洞**     | Broker/网关自身 CVE    | 中枢失守        |

## 5. 平台与云侧

### 5.1 设备身份与设备影子

- **设备身份**：`clientId`（唯一 ID）+ 凭据（用户名口令 / X.509 证书 / 预共享密钥）
- **设备影子（Device Twin）**：云端保存的"设备当前状态副本"（上报 + 期望状态），支持"影子下发"
- **理想状态**：
  - **一机一密/一机一证**，凭据可轮换、可吊销
  - **最小权限 ACL**（这台设备只能碰自己的 topic）
  - 凭据存**安全元件或受保护分区**，不存明文 Flash
- **现实状态**：大量平台**批量下发同一套账号口令**，泄露即"一人破全网"

### 5.2 OTA 升级体系

**IoT 设备唯一的安全更新通道**，要素：

| 要素                   | 说明                 | 缺失后果          |
| -------------------- | ------------------ | ------------- |
| **固件签名**             | 设备只接受**厂商私钥签名**的固件 | 中间人可刷后门       |
| **安全启动 Secure Boot** | 启动时校验签名            | 改 Flash 即持久后门 |
| **A/B 分区**           | 新固件写另一分区，验证成功才切换   | 变砖            |
| **回滚保护**             | 防降级到有漏洞的旧版本        | 已知漏洞被利用       |
| **分批灰度**             | 1% → 10% → 100%    | 一个坏固件瘫痪全网     |
| **强制/静默升级**          | 漏洞窗口最短             | 漏洞长期存在        |

> ⚠️ **签名验了 ≠ 安全**：还要管**密钥生命周期**（私钥在 HSM 里）、**证书吊销**、**降级防护**、**升级包本身不被篡改**。

### 5.3 数据侧

- **时序数据库（TSDB）**：高频时序写入，InfluxDB / TDengine / TimescaleDB

  > 💡 **对 OceanBase 大赛有启发**：时序是数据库的一个明确赛道，可作为延伸方向
- **规则引擎**：阈值告警、联动控制
- **流处理**：Kafka / Flink
- **数据安全**：个人位置、健康、家庭作息 → **《个人信息保护法》下的高敏感数据**

### 5.4 云端常见安全问题

| 问题                | 表现                         |
| ----------------- | -------------------------- |
| **API 未鉴权 / 鉴权弱** | 拿到 deviceId 就能读他人数据、控制他人设备 |
| **多租户隔离缺陷**       | A 租户能看到 B 租户设备             |
| **密钥明文存放**        | 数据库/日志/代码里明文存 accessKey    |
| **后台权限边界模糊**      | 运维能看全部设备数据                 |
| **日志缺失或泄露**       | 无审计 → 出事无法溯源               |
| **弱口令的老接口**       | 历史 API 没下线                 |

## 6. IoT 与网络安全的关系（核心）

### 6.1 为什么 IoT 是攻击者的"主粮"

**五个结构性原因**：

1. **数量巨大**：百亿量级，扫描成本极低
2. **出厂即默认**：默认口令、默认密钥、默认开放端口
3. **无人维护**：设备在客户家里/野外，公司根本碰不到
4. **生命周期超长**：2018 年的固件今天还在跑
5. **防护手段常缺席**：没加密、没签名、没验签、调试口没关
6. **物理可达**：设备在别人家里 → 物理接触机会（拆机、接 JTAG）

### 6.2 七层攻击面清单

| 层            | 攻击面                | 具体问题                                   |
| ------------ | ------------------ | -------------------------------------- |
| **① 硬件**     | 调试口、测试点、存储可读       | JTAG/SWD 未关、Flash 明文、eFuse 未烧、产线测试口保留  |
| **② 固件**     | 固件本身与升级            | 固件不加密、无 Secure Boot、OTA 无验签、降级无保护、隐藏后门 |
| **③ 系统/中间件** | Web/管理服务           | 命令注入、认证绕过、反序列化、默认账号、硬编码口令              |
| **④ 通信协议**   | MQTT/CoAP/HTTP/CAN | 明文传输、topic 越权、证书不校验、重放、无 ACL 的 Broker  |
| **⑤ 云平台**    | API 与多租户           | 越权访问、隔离缺陷、密钥明文、日志缺失                    |
| **⑥ 应用**     | App/Web/小程序        | 越权查询他人设备、Token 泄露、日志打印敏感信息             |
| **⑦ 供应链与运维** | 生产/分发/运维           | 出厂预置后门、批量共用密钥、内部运维权限过大、第三方云依赖          |

### 6.3 三条典型攻击链

**链 A：默认口令 → 僵尸网络（最经典）**

```
公网扫描（Shodan/Zenmap）→ 发现开放 Telnet/SSH 的 IoT
   → 用出厂默认口令字典批量登录（Mirai 的字典公开过）
   → 上传对应架构的载荷 → 设备加入 C2
   → 发起 DDoS / 挖矿 / 代理转发
```

**链 B：供应链 / 固件后门（最难发现）**

```
厂商生产环境被污染 → 固件出厂即带后门（隐藏账号 / 调试通道）
   → 用户设备永远"正常" → 后门长期存在
   → 通过 C2 静默下发指令
```

**链 C：云凭据 → 设备群接管**

```
云平台 accessKey 泄露（代码硬编码 / 日志泄露 / 前端包泄露）
   → 枚举设备 → 下发固件/指令 → 批量控制设备群
   → 破坏性后果（关门、断电、锁死）
```

> ⚠️ 这三条链**互相叠加**：链 A 拿下一台设备 → 链 C 里的云凭据进一步扩大战果。

### 6.4 经典案例（类型级）

> 只列公开报道的**类型**用于理解攻击链，不涉及任何在位设备。

| 类别                     | 说明                                                                           |
| ---------------------- | ---------------------------------------------------------------------------- |
| **Mirai 及其变种（2016 →）** | 源码泄露后衍生数百变种（Satori、Okiru 等）；Telnet 默认口令 + 多架构载荷 + C2 回收机制；把 IoT 设备变成 DDoS 主力 |
| **消费级路由器 RCE**         | Web 管理接口未授权命令注入、UPnP SOAP 解析缺陷（如 Realtek SDK 的 miniigd 缺陷被多个变种用于扩散）          |
| **摄像头/录像设备**           | 后门账号、Web 面板注入、弱口令；城市级摄像头网络被用于组建僵尸网络                                          |
| **工业控制系统**             | 历史上已有通过 USB/工控协议渗透的案例（Stuxnet 一类），后果是物理破坏                                    |
| **大规模蠕虫**              | 具备自传播能力的 IoT 蠕虫（利用可被蠕虫化的漏洞），2017 年 WannaCry/NotPetya 也波及大量路由器与摄像头            |
| **供应链投毒**              | 出厂固件/云平台被植入后门，用户无法察觉                                                         |
| **OTA 劫持**             | 不校验签名的升级通道 → 空中改写全网设备                                                        |
| **云侧数据泄露**             | 摄像头与定位数据被批量爬取，形成隐私灾难                                                         |

**共同规律**：**每一起事件的根因都不是"多高级的漏洞"，而是"最基本的配置没做对"。**

### 6.5 防御体系

**分层对应表**（攻击面 → 措施）：

| 层   | 关键措施                                                |
| --- | --------------------------------------------------- |
| 硬件  | 烧 eFuse 关 JTAG、开 RDP、Flash 加密、密钥存安全元件、产线测试口清除       |
| 固件  | **Secure Boot + 固件签名 + 降级防护 + A/B 分区**，依赖组件清单（SBOM） |
| 系统  | 关闭无用服务、默认口令强制修改、管理口只在内网、命令注入防护                      |
| 协议  | **全链路 TLS/DTLS**、Broker 开 ACL、**一机一密/一机一证**、防重放     |
| 云   | 最小权限 IAM、密钥托管（KMS）、租户隔离、审计日志、限流与配额                  |
| 应用  | 越权测试、Token 短有效期与轮换、敏感信息不落日志                         |
| 流程  | **资产清单**（知道自己在管的设备有多少）、漏洞响应 SLA、**分批灰度 OTA**、退役机制   |

**三个最值得先做的（性价比最高）**：

1. **资产可见**：先知道自己有多少设备、版本、暴露面（不然连补丁都不知道往哪打）
2. **默认口令清零 + 一机一密**
3. **OTA 签名验证 + 分批灰度**

### 6.6 标准与合规

| 标准 / 规范                           | 作用                                                                   |
| --------------------------------- | -------------------------------------------------------------------- |
| **OWASP IoT Top 10**              | 行业公认的风险清单，适合当自查表                                                     |
| **OWASP IoT 安全测试方法（OSTT / ISVS）** | 给了**可执行的验证步骤**（怎么测、测什么、怎么判过）                                         |
| **NISTIR 8259 系列**                | IoT 设备**安全能力基线**（设备应具备哪些能力：身份、更新、数据保护等）                              |
| **ETSI EN 303 645**               | 消费级 IoT 的**通用安全基线要求**（欧洲），涵盖默认口令、漏洞披露、OTA、存储保护等                      |
| **IEC 62443**                     | 工业自动化与控制系统安全（**工控方向**的标准主线）                                          |
| **国内合规**                          | 《网络安全法》《数据安全法》《个人信息保护法》；等保 2.0（GB/T 22239）；产品认证（CCRC/CCC）；关键信息基础设施要求 |

> 💡 **国内做 IoT 产品，这些不是选修课**——尤其《个保法》：摄像头、位置、健康数据都算个人信息。

## 11. 踩坑与排错

| 症状                    | 原因                        | 处理                                                   |
| --------------------- | ------------------------- | ---------------------------------------------------- |
| MQTTX 连不上 Broker      | 端口/ACL/防火墙/监听地址           | Broker 是否监听 `0.0.0.0`；`netstat -ano \| findstr 1883` |
| 能连上但收不到消息             | topic 不匹配、QoS/Retained 设置 | 用 `#` 订阅试试；确认是否用了 Retained                           |
| Wireshark 抓不到         | 走了 TLS(8883) 或加密          | 只能看到密文；改用明文端口做教学实验                                   |
| esp 端连不上 MQTT         | 主题/认证/字符编码                | 先用 MQTTX 验证 Broker 正常                                |
| Firmadyne 跑不起来        | 固件架构不匹配、缺库                | `check.sh` 识别架构；用对应 QEMU                             |
| Ghidra 里函数名全丢         | 固件未 strip                 | 只能手工分析；找 main 靠字符串引用                                 |
| 逻辑分析仪一片乱              | 没共地、采样率不足、线接反             | **必须共地**；降低采样率                                       |
| 串口无输出                 | 波特率/接错 USB 口/程序没跑到串口初始化   | 115200；S3/C3 分清原生 USB 与 UART 口                       |
| Android/iOS 上 MQTT 断开 | TLS 证书不被信任                | 用自签证书时客户端要导入 CA                                      |
